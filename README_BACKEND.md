# CQA backend

Подготовлены клиент Meta API, SQLite, чек-листы, импорт и расчёт, оценщик,
REST API, batch, апелляции и частичная переоценка. **Импорт и расчёт не требуют MODEL_API_KEY.**
Пользователь подтвердил реальный smoke test модели `muse-spark-1.3` с кодом выхода 0.
Контракт для фронтенда с фактическими примерами: [API_CONTRACT.md](API_CONTRACT.md).

## Установка и проверка

Python 3.11+. Команды из корня проекта в PowerShell:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
```

Для нового клона создайте `.env` на основе `.env.example`. В текущей рабочей папке
уже подготовлен `.env`: для обращений к модели вставьте ключ локально, не в чат.
Не заменяйте существующий заполненный `.env` шаблоном. `.env` и `.venv/` исключены из Git.

```powershell
.\.venv\Scripts\python.exe scripts/smoke_test.py
.\.venv\Scripts\python.exe -m pytest -q
```

Для другого расположения конфигурации:

```powershell
.\.venv\Scripts\python.exe scripts/smoke_test.py --env-file C:\path\to\.env
```

По умолчанию читается `.env` в корне этого проекта независимо от текущей папки.
Переменные процесса имеют приоритет над `.env`. Весь файл и ключ не логируются.

Скрипт делает один `chat.completions.create`, `timeout=60`, `max_retries=0`.
На вход модели передаётся только короткий тестовый запрос. Скрипт выводит текст,
фактически возвращённое имя модели и usage. При отсутствии usage выводится `null`,
а не придуманные нулевые токены. Для этапа 0 непустой текст и возвращённое имя модели
считаются успешной проверкой соединения; качество оценки диалогов проверяется позже.

Коды завершения: `0` — получен ответ; `1` — ошибка API, сети, SDK или ответа;
`2` — ошибка конфигурации. HTTP 401/403, 404, 429, 5xx и таймаут имеют понятные
сообщения. Ответы ошибок API и исходные исключения не печатаются, чтобы исключить
утечку заголовков или ключа. Повторов и подмены модели нет. Моки используются только
в тестах; они не подтверждают реальный доступ к модели.

## Если модель недоступна (404)

Сначала запросите список доступных ID тем же клиентом и через тот же `META_BASE_URL`:

```powershell
.\.venv\Scripts\python.exe scripts/list_models.py
```

Команда вызывает `client.models.list()` с `timeout=60`, `max_retries=0`. Требуется
`MODEL_API_KEY`, но `META_MODEL` для просмотра списка может быть пустым. Затем
замените `META_MODEL` в локальном `.env` на ID из ответа и самостоятельно повторите:

```powershell
.\.venv\Scripts\python.exe scripts/smoke_test.py
```

Если `/models` возвращает 404/405/501, команда сообщает, что маршрут недоступен
или не поддерживается. Это также может означать неверный `META_BASE_URL`.
Пустой ответ обозначается как пустой список; список не подменяется известными
названиями. Если API явно сообщает о следующей странице, команда возвращает ошибку
неполного списка, а не выдаёт его за полный. В таком случае проверьте доступную
модель и адрес в документации/кабинете провайдера. Тела ошибок и ключ не выводятся.

## Этап 1 без модели

Настройки в `.env.example`:

```dotenv
DATABASE_PATH=data/cqa.db
DATASET_API_URL=
DATASET_GROUP_ID=DEV
```

`DATABASE_PATH` по умолчанию разрешается относительно корня проекта, независимо
от текущей рабочей папки. Необязательный `MAX_DATASET_BYTES` ограничивает загрузку
(по умолчанию 20 МиБ). При превышении импорт завершается ошибкой без обрезания.
Подписанный URL организаторов храните только в `.env`; существующие query-параметры
сохраняются при установке `group_id`. Эти настройки независимы от настроек модели.

Создание БД и начального чек-листа:

```powershell
.\.venv\Scripts\python.exe scripts/init_db.py
```

При первом запуске создаются таблицы `conversations`, `messages`,
`checklist_versions`, `evaluations`, `evaluation_criteria`, `appeals`, `decisions`,
`llm_calls`, `jobs`, а также служебная `app_settings`. Seed содержит ровно восемь
критериев из `backend/configs/default_checklist.json`. Повторный запуск сохраняет
диалоги и выбранную пользователем версию. Внешние ключи включены на каждом соединении.
Изменение и удаление сохранённых версий чек-листа запрещены SQLite-триггерами.

Загрузка DEV и контрольного набора по GET API:

```powershell
.\.venv\Scripts\python.exe scripts/load_dataset.py
.\.venv\Scripts\python.exe scripts/load_dataset.py --group-id CONTROL_ID_FROM_ORGANIZERS
```

Импорт уже полученного JSON-ответа без сети (включая присланный текстовый файл):

```powershell
.\.venv\Scripts\python.exe scripts/load_dataset.py --file "C:\path\to\DEV.json"
```

Файл должен содержать исходную оболочку `error/isSuccess/data`, а не только массив
диалогов. Для файла группа берётся из `data.dataset_group_id`; `--group-id` позволяет
дополнительно проверить её. Результат показывает `inserted`, `updated`, `unchanged`,
общее число и предупреждения. Повторный идентичный импорт не создаёт дубликатов.
Проверяются `isSuccess`, `error`, число записей, роли, языки, каналы и уникальность ID.
Некорректная запись отменяет импорт всего набора; изменения сохраняются транзакцией.

Идентификаторы реплик — `m1`, `m2`, … по порядку массива. `timestamp` и `text`
сохраняются без изменения; реплики `bot`/`system` не удаляются. У чатов `offset_sec`
равен null. У звонков это разница с первой репликой по ISO 8601 с учётом часового пояса.
Неверный ISO или отсутствие часового пояса дают null и предупреждение; при неверной
первой метке все смещения остаются null. Импорт при этом продолжается.

При изменении содержимого диалога upsert обновляет его реплики и увеличивает
`revision`. Схема результатов предусматривает снимок транскрипта и номер ревизии,
чтобы будущие оценки оставались связаны с исходными доказательствами.

## Версии и расчёт баллов

Внутренние Python-интерфейсы (HTTP-маршруты появятся на этапе API):

```python
from backend.db import connect_db, init_db
from backend.checklist import get_checklist, save_checklist, activate_checklist
from backend.scoring import calculate_scores

init_db()
conn = connect_db()
try:
    current = get_checklist(conn)
    # Передайте изменённую конфигурацию: каждое сохранение создаёт новую версию.
    # updated = save_checklist(conn, changed_config, checklist_id=current['checklist_id'])
    # result = calculate_scores(current, answers_by_criterion_id)
finally:
    conn.close()
```

Сохранение валидирует типы, уникальность ID, секции, неотрицательные конечные веса,
числовые ступени шкалы, правила флагов и условие N/A. Новая версия становится активной
атомарно; старые версии остаются доступными по ID. `weight_sum` возвращается десятичной
строкой и учитывает только активные scored-критерии. Дробные веса также сохраняются
точно десятичными строками. Новые критерии применяются без изменения кода.

`calculate_scores(checklist, answers)` принимает ответы по ID всех активных критериев
и возвращает Decimal-значения. Для yes_no: yes даёт вес, no — 0. Для шкалы:
`earned = weight * value / max(scale)`. N/A исключается из знаменателя.
`total = sum(earned) / sum(applicable_weights) * 100`; если знаменатель нулевой,
результат null. Флаги не входят в числовой итог; любой активный yes-флаг устанавливает
`gross_violation`. Расчёт не содержит специальных правил для конкретных ID.

Возвращаются `total`, `gross_violation`, `criteria` и `sections`. Критерий содержит
`earned`, `effective_weight`, `points`; секция — `section_score`. Округление итогов и
нормированных значений — `ROUND_HALF_UP` до двух знаков, без промежуточного округления
сумм. Для N/A/неоцениваемого критерия earned=null, effective_weight=points=0.
При нулевом применимом весе нормированные значения применимых критериев также null.
Недопустимые и пропущенные ответы вызывают ошибку, без придумывания оценок.

## Этап 2: оценка одного диалога

Укажите ключ и модель в локальном `.env`. Один штатный запуск делает один запрос
на весь диалог. Дополнительные вызовы возможны только для ограниченных транспортных
повторов, отключения неподдержанного JSON mode или одного исправления ответа.
Рантайм не имеет режима фиктивной оценки.

```powershell
.\.venv\Scripts\python.exe scripts/evaluate_one.py p1-ru-003
.\.venv\Scripts\python.exe scripts/evaluate_one.py p1-kz-001 --lang kk
.\.venv\Scripts\python.exe scripts/evaluate_one.py p1-en-001 --lang en
```

`--lang ru|kk|en` задаёт язык объяснений, а не язык исходного диалога. По умолчанию
`ru`. `--checklist-version-id` выбирает сохранённую версию; по умолчанию активную.
Тексты обоих системных промптов сохранены дословно из задания; код заменяет только
`{output_language}`. Промпт содержит только активные критерии и экранированный
транскрипт между `<transcript>`/`</transcript>`. Роли и исходные данные в БД не меняются.
Комментарии/текст реплик не могут добавить сообщения SDK с ролью system.

Настройки (можно добавить в существующий `.env`, не заменяя ключ):

```dotenv
LLM_MAX_TOKENS=8192
LLM_MAX_INPUT_CHARS=100000
LLM_TIMEOUT_SECONDS=120
LLM_USE_SYSTEM_TRUST=true
PRICE_INPUT_PER_1M=
PRICE_OUTPUT_PER_1M=
```

Лимит выходных токенов включает скрытые рассуждения модели. Ответ с
`finish_reason=length` или иным завершением, отличным от `stop`, не оценивается:
сохраняются ошибка, сырое содержимое и предоставленные токены. Длинный вход
отклоняется с `MODEL_INPUT_TOO_LARGE`, без обрезания транскрипта.
`LLM_USE_SYSTEM_TRUST=true` использует системные доверенные сертификаты через
`ssl.create_default_context()`; проверка сертификата и имени узла остаётся включённой.
Это необходимо в окружениях Windows, где цепочка сертификата доступна системному
хранилищу, но не набору certifi. Значение false оставляет стандартный TLS-клиент SDK.
Диагностические smoke/list-команды сохраняют прежнее поведение SDK.

Транспортные ограничения: 401/403/404 — без повторов; 429 — до четырёх попыток;
5xx и таймауты — до трёх. Backoff экспоненциальный с jitter и учётом `Retry-After`.
`response_format={"type":"json_object"}` отправляется при первой оценке. Только явная
ошибка этого параметра приводит к повтору без него и сохранению признака
неподдержки по паре endpoint/model. Иные ошибки 400 не маскируются этим переключением.

Валидация проверяет ID диалога, точное покрытие критериев, разрешённые ответы,
ступени шкалы, цитаты в конкретных репликах, существование и порядок диапазонов.
Для сравнения цитат нормализуются пробелы, регистр, типографские кавычки и тире;
показанная цитата не исправляется. К доказательству добавляется исходная роль.
JSON допускается в одном внешнем Markdown-ограждении с языком `json`; произвольный текст вокруг,
повторные JSON-ключи и NaN/Infinity отвергаются.

При ошибке валидации отправляется ровно один исправляющий запрос с перечнем ошибок.
После повторной ошибки — `needs_review`: валидные критерии последнего ответа
сохраняются, невалидные имеют answer=null и список ошибок. Общий итог, нормированные
веса/баллы и баллы секций остаются null: неполный набор не выдаётся за полный.
Предыдущие ответы сохранены отдельно, результаты разных попыток не смешиваются.
Ошибка API даёт `failed`, без фиктивных баллов. Код завершения CLI: completed=0,
needs_review=2, failed=1. Изменения итогового результата и критериев атомарны.

Каждый физический вызов записывается в `llm_calls`: назначение, попытка, HTTP/error
code, длительность, finish_reason, сырое содержимое, usage, применённые цены и стоимость.
Диалог хранится снимком вместе с ревизией и неизменяемой версией чек-листа.
Сырые ответы хранятся в локальной БД, но не пишутся в INFO-логи. Исходные и финальные
результаты хранятся раздельно; пересмотр появится на этапе апелляций.

Стоимость вызова:
`(prompt_tokens * PRICE_INPUT_PER_1M + completion_tokens * PRICE_OUTPUT_PER_1M) / 1000000`.
Валюта соответствует введённым ценам. Без обеих цен выводится «цена не задана».
Суммарные токены включают все известные usage, в том числе исправления и обрезанные
ответы. Если usage какого-либо вызова отсутствует, выводится предупреждение о
неполноте; полный расход и стоимость не выдаются за известные. Сводка не является
счётом провайдера.

Полный аудит (транскрипт, все сырые ответы, ошибки проверки, вызовы, итог и токены):

```powershell
.\.venv\Scripts\python.exe scripts/evaluate_one.py p1-ru-003 --audit --report-dir data/reports/stage2
```

JSON/TXT-отчёты имеют ID оценки в имени и создаются без перезаписи. Подписанная
ссылка на аудиозапись исключается из экспорта. Повторный просмотр уже сохранённого
результата без новых запросов и расходов:

```powershell
.\.venv\Scripts\python.exe scripts/evaluate_one.py EVALUATION_ID --saved --audit
```

Диагностические JSON/TXT и SQLite находятся в игнорируемой папке `data/`.
Схема старой БД расширяется идемпотентной миграцией; данные этапа 1 сохраняются.

У p1-ru-003 первый ответ не содержал evidence к частичной оценке консультации;
один исправляющий запрос устранил ошибку. Остальные четыре прошли с первого ответа.
В p1-ru-001 идентификация оценена как N/A. В этих пяти результатах gross_violation=false.

Причина устранена использованием проверяемого системного хранилища сертификатов.
Полные транскрипты, сырые ответы и история проверок — в локальных отчётах
`data/reports/stage2/`. Это техническая проверка, а не измерение точности по Ground Truth.

## Структура

- `backend/config.py` — конфигурация и проверка обязательных настроек.
- `backend/meta_client.py` — `ask_meta(system_prompt, user_prompt)`.
- `scripts/smoke_test.py` — реальная проверка API.
- `tests/test_smoke_test.py` — ошибки, отсутствие секретов в выводе, число вызовов.
- `scripts/list_models.py` — просмотр реально возвращённых API ID моделей.
- `backend/db.py` — схема, соединения и транзакции SQLite.
- `backend/checklist.py`, `backend/configs/default_checklist.json` — версии и seed.
- `backend/dataset.py` — API организаторов, нормализация и upsert.
- `backend/scoring.py` — чистый расчёт на Decimal.
- `scripts/init_db.py`, `scripts/load_dataset.py` — проверка этапа 1 из терминала.
- `backend/llm_client.py` — ограниченные повторы, аудит вызовов и стоимость.
- `backend/validation.py` — JSON, критерии, диапазоны и доказательства.
- `backend/evaluator.py` — оценка одного диалога и сохранение результата.
- `backend/prompts/` — выданные системные промпты оценщика и апелляции.
- `scripts/evaluate_one.py` — оценка и экспорт аудита.

## Допущения

- Скелета в исходной папке не было; это подтверждено пользователем. Код клиента
  расположен в `backend/` по запрошенной структуре. Существующие файлы не заменялись.
- `https://api.meta.ai/v1` и `muse-spark-1.3` взяты из задания и проверены реальными
  запросами. Другие адреса и модели автоматически не подбираются.
- Используется только стандартный вызов Chat Completions из заявленного скелета.
  JSON mode принят провайдером на реальных проверках; при явном отказе параметра
  клиент сохраняет обнаруженную несовместимость и разбирает текстовый JSON.
- Цена одной оценки и статистика `/api/stats/cost` используют сохранённые тарифы
  каждого вызова. Значения цен не подставляются автоматически.
- Первая реакция за 3 минуты не участвует в оценке: это прямо исключено PDF-чек-листом.
- У шкал допускаются минимум две различные неотрицательные числовые ступени,
  максимум должен быть положительным. Отрицательные/нулевые максимумы сделали бы
  формулу баллов некорректной. N/A не разрешается для flag даже при ошибочном конфиге.
- Для формального критерия «низкая ступень» используется любое значение scale ниже
  максимума. Для N/A требуется явная цитата полного na_condition в reasoning:
  код может проверить ссылку на правило, но не доказать истинность смыслового вывода.
  При объяснениях kk/en условие цитируется на исходном языке конфигурации.
- Наличие цитаты в транскрипте не гарантирует правильность интерпретации. Точность
  оценок относительно Ground Truth ещё должна измеряться отдельно.
- Проверка цитат подтверждает их наличие, а не смысловую правильность вывода.
  AI-подсказка не заменяет решение проверяющего.

## REST API и batch — этап 3

```powershell
.\.venv\Scripts\python.exe -m uvicorn backend.main:app --host 127.0.0.1 --port 8001
```

Локальный совместимый запуск `uvicorn main:app --reload --port 8001` доступен через
корневой `main.py`, который оставлен вне Git по решению владельца проекта.
После клонирования используйте основной запуск `uvicorn backend.main:app --port 8001`.
Swagger: http://127.0.0.1:8001/docs. Health: `/api/health`.
Запускайте **один worker**: очередь и ограничения параллельности обслуживаются одним
процессом. `--reload` удобен для разработки, но перезапуск во время оценки может
прервать задачу. Каждый запуск помечает незавершённые задачи `interrupted`;
автоматического повтора оплачиваемых запросов после сбоя нет.

`CORS_ORIGINS=*` для разработки либо список origin через запятую. Cookie credentials
не включены. `MAX_CONCURRENCY=4` ограничивает одновременно работающие элементы всех
batch-задач. Блокирующий SDK работает в потоках, event loop остаётся доступным.
Готовые оценки той же версии чек-листа и редакции диалога пропускаются, если
`force=false`; изменение транскрипта требует новой оценки. Язык объяснений не входит
в ключ идемпотентности: для его смены используйте `force=true`.

Задача возвращает `job_id` сразу. `done` включает успехи, пропуски и ошибки;
`errors` и `items` объясняют результат каждого диалога. `completed` у job означает
окончание обработки, поэтому проверяйте также `errors` и статусы оценок.
`needs_review` сохраняет валидные ответы, но итог `null`, без искусственного
перераспределения веса только на успешно проверенные критерии.

```powershell
$base = 'http://127.0.0.1:8001'
Invoke-RestMethod "$base/api/health"
Invoke-RestMethod "$base/api/dataset/load" -Method Post -ContentType 'application/json' -Body '{"group_id":"DEV"}'
$job = Invoke-RestMethod "$base/api/evaluations/batch" -Method Post -ContentType 'application/json' -Body '{"conversation_ids":["p1-ru-001","p1-en-001"],"output_language":"ru"}'
Invoke-RestMethod "$base/api/jobs/$($job.job_id)"
```

Для контрольного набора укажите полученный от организаторов group_id в запросе
загрузки либо `DATASET_GROUP_ID` в `.env`. Действительный `DATASET_API_URL` обязателен:
при отсутствии возвращается HTTP 503 `DATASET_NOT_CONFIGURED`, данные не имитируются.
Одиночная загрузка поддерживает JSON и `text/plain` со строками `role: text`;
неизвестное время — пустая строка. `MAX_DATASET_BYTES` ограничивает тело загрузки
до разбора JSON; `LLM_MAX_INPUT_CHARS` ограничивает вход модели без обрезки.

## Апелляции и переоценка — этап 4

Апелляция открывается по сохранённому валидному критерию. Карточка содержит
спорный ответ, исходный итог, две соседние реплики вокруг каждого доказательства
и весь `checked_range`. Для одного критерия допускается одна открытая апелляция.
AI-рекомендация проходит проверку значений, ID и цитат, сохраняется в аудите вызовов
и не изменяет ответы. Решение `confirm` сохраняет ответ, `change` обязано изменить;
оба требуют причину. Повторное решение возвращает 409.

`original` и исходные ответы неизменяемы. Решение пересчитывает `final`, хранит
`before_total` и `after_total`. Новые цитаты от имени проверяющего не выдумываются:
ручной ответ помечен `source=reviewer`, исходные доказательства доступны в `original`.
Актуальные токены, включая AI-подсказки, берите из верхнего `usage` карточки.

Сохранение чек-листа создаёт и активирует новую версию; ответ содержит `change_summary`.
Вызов модели необходим для добавленных/активированных критериев и изменений `name`,
`description`, `type`, `allow_na`, `na_condition`, `yes_text`, `no_text`, `scale`.
Изменение только веса, участия в расчёте, секции или порядка требует пересчёта.
Удалённые и отключённые критерии исключаются.

В batch передайте `criterion_ids: ["05"]` для изменённого критерия или `[]` для
автоматического diff/пересчёта. Оставьте поле отсутствующим для полной оценки.
Базой служит последняя валидная completed-оценка по более ранней версии того же
чек-листа и той же редакции транскрипта. Используется её финальный слой с решениями
проверяющего. Если подходящей базы нет — оценивается весь чек-лист. Все семантически
изменённые/добавленные критерии автоматически включаются, даже если их забыли в списке.
Чисто весовые изменения не вызывают модель даже при указании их ID.
Итог всегда рассчитывается по полному новому чек-листу.

В `reevaluation` видны база, реально оценённые и перенесённые ID. Перенесённые
объяснения сохраняют прежний язык, указанный в `baseline_output_language`.
При чистом пересчёте токены и стоимость равны известному нулю — запросов не было.
При неизвестном usage после ошибки сумма неполна: `usage_complete=false`.

## Ограничения прототипа

- Один процесс API, SQLite и локальная очередь; распределённого планировщика нет.
- Авторизация пользователей и разграничение ролей не реализованы; сервер по умолчанию
  слушает localhost. Доступ к решениям проверяющего в прототипе не разграничен.
- Прерванные jobs не возобновляются автоматически. Повторите batch после проверки
  `items`; уже готовые элементы будут пропущены.
- Списки пока без пагинации; подходят для набора хакатона.
- Денежная единица соответствует введённым ценам провайдера; автоматически не определяется.
- Реальные результаты могут различаться между вызовами. Валидация структуры и цитат
  не измеряет точность относительно Ground Truth.
