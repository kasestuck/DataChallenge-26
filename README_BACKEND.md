# CQA backend

Подготовлены клиент Meta API, SQLite, чек-листы, импорт и расчёт, оценщик,
REST API, batch, апелляции и частичная переоценка. **Импорт и расчёт не требуют MODEL_API_KEY.**
Пользователь подтвердил реальный smoke test модели `muse-spark-1.3` с кодом выхода 0.
Контракт для фронтенда: [API_CONTRACT.md](API_CONTRACT.md). Структура и числа взяты
из фактических захватов; тексты реплик и содержательных объяснений в документации
синтетические и не относятся к диалогам организаторов.

## Установка и проверка

Python 3.11+. Команды из корня проекта в PowerShell:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
if (-not (Test-Path -LiteralPath '.env')) {
    Copy-Item -LiteralPath '.env.example' -Destination '.env'
}
```

Команда выше создаёт `.env` из шаблона только при его отсутствии. Все прямые
зависимости, включая pytest, зафиксированы точными версиями в requirements-файлах.
В новом клоне MODEL_API_KEY пуст: health и тесты работают без реального ключа,
а smoke test до его заполнения должен вернуть ошибку конфигурации, не успех.
Для обращений к модели вставьте ключ локально, не в чат.
Не заменяйте существующий заполненный `.env` шаблоном. `.env` и `.venv/` исключены из Git.

```powershell
.\.venv\Scripts\python.exe scripts/smoke_test.py
.\.venv\Scripts\python.exe -m pytest -q
```

Для другого расположения конфигурации:

```powershell
.\.venv\Scripts\python.exe scripts/smoke_test.py --env-file C:\path\to\.env
```

По умолчанию читается `.env` в корне этого проекта независимо от текущей папки.
Переменные процесса имеют приоритет над `.env`. Весь файл и ключ не логируются.

Скрипт делает один `chat.completions.create`, `timeout=60`, `max_retries=0`.
На вход модели передаётся только короткий тестовый запрос. Скрипт выводит текст,
фактически возвращённое имя модели и usage. При отсутствии usage выводится `null`,
а не придуманные нулевые токены. Для этапа 0 непустой текст и возвращённое имя модели
считаются успешной проверкой соединения; качество оценки диалогов проверяется позже.

Коды завершения: `0` — получен ответ; `1` — ошибка API, сети, SDK или ответа;
`2` — ошибка конфигурации. HTTP 401/403, 404, 429, 5xx и таймаут имеют понятные
сообщения. Ответы ошибок API и исходные исключения не печатаются, чтобы исключить
утечку заголовков или ключа. Повторов и подмены модели нет. Моки используются только
в тестах; они не подтверждают реальный доступ к модели.

## Если модель недоступна (404)

Сначала запросите список доступных ID тем же клиентом и через тот же `META_BASE_URL`:

```powershell
.\.venv\Scripts\python.exe scripts/list_models.py
```

Команда вызывает `client.models.list()` с `timeout=60`, `max_retries=0`. Требуется
`MODEL_API_KEY`, но `META_MODEL` для просмотра списка может быть пустым. Затем
замените `META_MODEL` в локальном `.env` на ID из ответа и самостоятельно повторите:

```powershell
.\.venv\Scripts\python.exe scripts/smoke_test.py
```

Если `/models` возвращает 404/405/501, команда сообщает, что маршрут недоступен
или не поддерживается. Это также может означать неверный `META_BASE_URL`.
Пустой ответ обозначается как пустой список; список не подменяется известными
названиями. Если API явно сообщает о следующей странице, команда возвращает ошибку
неполного списка, а не выдаёт его за полный. В таком случае проверьте доступную
модель и адрес в документации/кабинете провайдера. Тела ошибок и ключ не выводятся.

## Настройка модели, цен и лимитов

Все настройки берутся из локального `.env`; переменные процесса имеют приоритет.
Для смены модели измените только `META_MODEL` на доступный ID, затем выполните smoke test.
Автоматического перехода на другую модель нет. Старые вызовы сохраняют фактически
использованное имя модели и тарифы; изменение `.env` не пересчитывает историческую стоимость.

## Этап 1 без модели

Настройки в `.env.example`:

```dotenv
DATABASE_PATH=data/cqa.db
DATASET_API_URL=
DATASET_GROUP_ID=DEV
```

`DATABASE_PATH` по умолчанию разрешается относительно корня проекта, независимо
от текущей рабочей папки. Необязательный `MAX_DATASET_BYTES` ограничивает загрузку
(по умолчанию 20 МиБ). При превышении импорт завершается ошибкой без обрезания.
Подписанный URL организаторов храните только в `.env`; существующие query-параметры
сохраняются при установке `group_id`. Эти настройки независимы от настроек модели.

Создание БД и начального чек-листа:

```powershell
.\.venv\Scripts\python.exe scripts/init_db.py
```

При первом запуске создаются таблицы `conversations`, `messages`,
`checklist_versions`, `evaluations`, `evaluation_criteria`, `appeals`, `decisions`,
`llm_calls`, `jobs`, а также служебная `app_settings`. Seed содержит ровно восемь
критериев из `backend/configs/default_checklist.json`. Повторный запуск сохраняет
диалоги и выбранную пользователем версию. Внешние ключи включены на каждом соединении.
Изменение и удаление сохранённых версий чек-листа запрещены SQLite-триггерами.

Загрузка DEV и контрольного набора по GET API:

```powershell
.\.venv\Scripts\python.exe scripts/load_dataset.py
.\.venv\Scripts\python.exe scripts/load_dataset.py --group-id CONTROL_ID_FROM_ORGANIZERS
```

Импорт уже полученного JSON-ответа без сети (включая присланный текстовый файл):

```powershell
.\.venv\Scripts\python.exe scripts/load_dataset.py --file "C:\path\to\DEV.json"
```

Файл должен содержать исходную оболочку `error/isSuccess/data`, а не только массив
диалогов. Для файла группа берётся из `data.dataset_group_id`; `--group-id` позволяет
дополнительно проверить её. Результат показывает `inserted`, `updated`, `unchanged`,
общее число и предупреждения. Повторный идентичный импорт не создаёт дубликатов.
Проверяются `isSuccess`, `error`, число записей, роли, языки, каналы и уникальность ID.
Некорректная запись отменяет импорт всего набора; изменения сохраняются транзакцией.

Идентификаторы реплик — `m1`, `m2`, … по порядку массива. `timestamp` и `text`
сохраняются без изменения; реплики `bot`/`system` не удаляются. У чатов `offset_sec`
равен null. У звонков это разница с первой репликой по ISO 8601 с учётом часового пояса.
Неверный ISO или отсутствие часового пояса дают null и предупреждение; при неверной
первой метке все смещения остаются null. Импорт при этом продолжается.

При изменении содержимого диалога upsert обновляет его реплики и увеличивает
`revision`. Схема результатов предусматривает снимок транскрипта и номер ревизии,
чтобы будущие оценки оставались связаны с исходными доказательствами.

## Версии и расчёт баллов

Внутренние Python-интерфейсы; соответствующие HTTP-маршруты описаны в API_CONTRACT.md:

```python
from backend.db import connect_db, init_db
from backend.checklist import get_checklist, save_checklist, activate_checklist
from backend.scoring import calculate_scores

init_db()
conn = connect_db()
try:
    current = get_checklist(conn)
    # Передайте изменённую конфигурацию: каждое сохранение создаёт новую версию.
    # updated = save_checklist(conn, changed_config, checklist_id=current['checklist_id'])
    # result = calculate_scores(current, answers_by_criterion_id)
finally:
    conn.close()
```

Сохранение валидирует типы, уникальность ID, секции, неотрицательные конечные веса,
числовые ступени шкалы, правила флагов и условие N/A. Новая версия становится активной
атомарно; старые версии остаются доступными по ID. `weight_sum` возвращается десятичной
строкой и учитывает только активные scored-критерии. Дробные веса также сохраняются
точно десятичными строками. Новые критерии применяются без изменения кода.

`calculate_scores(checklist, answers)` принимает ответы по ID всех активных критериев
и возвращает Decimal-значения. Для yes_no: yes даёт вес, no — 0. Для шкалы:
`earned = weight * value / max(scale)`. N/A исключается из знаменателя.
`total = sum(earned) / sum(applicable_weights) * 100`; если знаменатель нулевой,
результат null. Флаги не входят в числовой итог; любой активный yes-флаг устанавливает
`gross_violation`. Расчёт не содержит специальных правил для конкретных ID.

Возвращаются `total`, `gross_violation`, `criteria` и `sections`. Критерий содержит
`earned`, `effective_weight`, `points`; секция — `section_score`. Округление итогов и
нормированных значений — `ROUND_HALF_UP` до двух знаков, без промежуточного округления
сумм. Для N/A/неоцениваемого критерия earned=null, effective_weight=points=0.
При нулевом применимом весе нормированные значения применимых критериев также null.
Недопустимые и пропущенные ответы вызывают ошибку, без придумывания оценок.

## Этап 2: оценка одного диалога

Укажите ключ и модель в локальном `.env`. Один штатный запуск делает один запрос
на весь диалог. Дополнительные вызовы возможны только для ограниченных транспортных
повторов, отключения неподдержанного JSON mode или одного исправления ответа.
Рантайм не имеет режима фиктивной оценки.

```powershell
.\.venv\Scripts\python.exe scripts/evaluate_one.py p1-ru-003
.\.venv\Scripts\python.exe scripts/evaluate_one.py p1-kz-001 --lang kk
.\.venv\Scripts\python.exe scripts/evaluate_one.py p1-en-001 --lang en
```

`--lang ru|kk|en` задаёт язык объяснений, а не язык исходного диалога. По умолчанию
`ru`. `--checklist-version-id` выбирает сохранённую версию; по умолчанию активную.
Системные промпты основаны на задании; в оценщике добавлены согласованные уточнения
по двойному штрафу и идентификации. Код подставляет `{output_language}`. Пользовательский
промпт содержит только активные критерии и экранированный
транскрипт между `<transcript>`/`</transcript>`. Роли и исходные данные в БД не меняются.
Комментарии/текст реплик не могут добавить сообщения SDK с ролью system.

Настройки (можно добавить в существующий `.env`, не заменяя ключ):

```dotenv
LLM_MAX_TOKENS=8192
LLM_MAX_INPUT_CHARS=100000
LLM_TIMEOUT_SECONDS=120
LLM_USE_SYSTEM_TRUST=true
PRICE_INPUT_PER_1M=
PRICE_OUTPUT_PER_1M=
```

Лимит выходных токенов включает скрытые рассуждения модели. Ответ с
`finish_reason=length` или иным завершением, отличным от `stop`, не оценивается:
сохраняются ошибка, сырое содержимое и предоставленные токены. Длинный вход
отклоняется с `MODEL_INPUT_TOO_LARGE`, без обрезания транскрипта.
`LLM_USE_SYSTEM_TRUST=true` использует системные доверенные сертификаты через
`ssl.create_default_context()`; проверка сертификата и имени узла остаётся включённой.
Это необходимо в окружениях Windows, где цепочка сертификата доступна системному
хранилищу, но не набору certifi. Значение false оставляет стандартный TLS-клиент SDK.
Диагностические smoke/list-команды сохраняют прежнее поведение SDK.

Транспортные ограничения: 401/403/404 — без повторов; 429 — до четырёх попыток;
5xx и таймауты — до трёх. Backoff экспоненциальный с jitter и учётом `Retry-After`.
`response_format={"type":"json_object"}` отправляется при первой оценке. Только явная
ошибка этого параметра приводит к повтору без него и сохранению признака
неподдержки по паре endpoint/model. Иные ошибки 400 не маскируются этим переключением.

Валидация проверяет ID диалога, точное покрытие критериев, разрешённые ответы,
ступени шкалы, цитаты в конкретных репликах, существование и порядок диапазонов.
Для сравнения цитат нормализуются пробелы, регистр, типографские кавычки и тире;
показанная цитата не исправляется. К доказательству добавляется исходная роль.
JSON допускается в одном внешнем Markdown-ограждении с языком `json`; произвольный текст вокруг,
повторные JSON-ключи и NaN/Infinity отвергаются.

При ошибке валидации отправляется ровно один исправляющий запрос с перечнем ошибок.
После повторной ошибки — `needs_review`: валидные критерии последнего ответа
сохраняются, невалидные имеют answer=null и список ошибок. Общий итог, нормированные
веса/баллы и баллы секций остаются null: неполный набор не выдаётся за полный.
Предыдущие ответы сохранены отдельно, результаты разных попыток не смешиваются.
Ошибка API даёт `failed`, без фиктивных баллов. Код завершения CLI: completed=0,
needs_review=2, failed=1. Изменения итогового результата и критериев атомарны.

Каждый физический вызов записывается в `llm_calls`: назначение, попытка, HTTP/error
code, длительность, finish_reason, сырое содержимое, usage, применённые цены и стоимость.
Диалог хранится снимком вместе с ревизией и неизменяемой версией чек-листа.
Сырые ответы хранятся в локальной БД, но не пишутся в INFO-логи. Исходные и финальные
результаты хранятся раздельно; пересмотр реализован через API апелляций.

Стоимость вызова:
`(prompt_tokens * PRICE_INPUT_PER_1M + completion_tokens * PRICE_OUTPUT_PER_1M) / 1000000`.
Валюта соответствует введённым ценам. Без обеих цен выводится «цена не задана».
Суммарные токены включают все известные usage, в том числе исправления и обрезанные
ответы. Если usage какого-либо вызова отсутствует, выводится предупреждение о
неполноте; полный расход и стоимость не выдаются за известные. Сводка не является
счётом провайдера.

Полный аудит (транскрипт, все сырые ответы, ошибки проверки, вызовы, итог и токены):

```powershell
.\.venv\Scripts\python.exe scripts/evaluate_one.py p1-ru-003 --audit --report-dir data/reports/stage2
```

JSON/TXT-отчёты имеют ID оценки в имени и создаются без перезаписи. Подписанная
ссылка на аудиозапись исключается из экспорта. Повторный просмотр уже сохранённого
результата без новых запросов и расходов:

```powershell
.\.venv\Scripts\python.exe scripts/evaluate_one.py EVALUATION_ID --saved --audit
```

Диагностические JSON/TXT и SQLite находятся в игнорируемой папке `data/`.
Схема старой БД расширяется идемпотентной миграцией; данные этапа 1 сохраняются.

## Допущения

- Проверены исходные JSON всех 65 DEV-записей: поля только `conversation_id`,
  `channel`, `language`, `transcript`, `audio_url`. Поля каждой из 1268 реплик:
  `speaker`, `text`, `timestamp`. Эталонной разметки в этих записях нет.
  Отчёты характеризуют формальную валидность, расход и повторяемость. После заполнения
  человеком таблицы сравнение называется «согласие с ручной разметкой на выборке».
- Каждая новая оценка сохраняет `prompt_hash` — SHA-256 байтов файла системного
  промпта, использованного в этом запросе. У прежних оценок хэш остаётся null:
  задним числом версия не приписывается. При переносе ответов из предыдущей оценки
  `baseline_prompt_hash` отдельно показывает происхождение этих ответов.

- Скелета в исходной папке не было; это подтверждено пользователем. Код клиента
  расположен в `backend/` по запрошенной структуре. Существующие файлы не заменялись.
- `https://api.meta.ai/v1` и `muse-spark-1.3` взяты из задания и проверены реальными
  запросами. Другие адреса и модели автоматически не подбираются.
- Используется только стандартный вызов Chat Completions из заявленного скелета.
  JSON mode принят провайдером на реальных проверках; при явном отказе параметра
  клиент сохраняет обнаруженную несовместимость и разбирает текстовый JSON.
- Цена одной оценки и статистика `/api/stats/cost` используют сохранённые тарифы
  каждого вызова. Значения цен не подставляются автоматически.
- Первая реакция за 3 минуты не участвует в оценке: это прямо исключено PDF-чек-листом.
- У шкал допускаются минимум две различные неотрицательные числовые ступени,
  максимум должен быть положительным. Отрицательные/нулевые максимумы сделали бы
  формулу баллов некорректной. N/A не разрешается для flag даже при ошибочном конфиге.
- Для формального критерия «низкая ступень» используется любое значение scale ниже
  максимума. Для N/A требуется явная цитата полного na_condition в reasoning:
  код может проверить ссылку на правило, но не доказать истинность смыслового вывода.
  При объяснениях kk/en условие цитируется на исходном языке конфигурации.
- Наличие цитаты в транскрипте не гарантирует правильность интерпретации. Точность
  оценок относительно Ground Truth ещё должна измеряться отдельно.
- Проверка цитат подтверждает их наличие, а не смысловую правильность вывода.
  AI-подсказка не заменяет решение проверяющего.

## REST API и batch — этап 3

```powershell
.\.venv\Scripts\python.exe -m uvicorn backend.main:app --host 127.0.0.1 --port 8001
```

Приложение определено в `backend/main.py`. Команда выше — единая команда запуска
для локальной работы и клонированного проекта. Корневой `main.py` содержит только
импорт приложения для совместимости; отдельного приложения в нём нет.
Swagger: http://127.0.0.1:8001/docs. Health: `/api/health`.
Запускайте **один worker**: очередь и ограничения параллельности обслуживаются одним
процессом. `--reload` удобен для разработки, но перезапуск во время оценки может
прервать задачу. Каждый запуск помечает незавершённые задачи `interrupted`;
автоматического повтора оплачиваемых запросов после сбоя нет.

`CORS_ORIGINS=*` для разработки либо список origin через запятую. Cookie credentials
не включены. `MAX_CONCURRENCY=4` ограничивает одновременно работающие элементы всех
batch-задач. Блокирующий SDK работает в потоках, event loop остаётся доступным.
Готовые оценки той же версии чек-листа и редакции диалога пропускаются, если
`force=false`; изменение транскрипта требует новой оценки. Язык объяснений не входит
в ключ идемпотентности: для его смены используйте `force=true`.

Задача возвращает `job_id` сразу. `done` включает успехи, пропуски и ошибки;
`errors` и `items` объясняют результат каждого диалога. `completed` у job означает
окончание обработки, поэтому проверяйте также `errors` и статусы оценок.
`needs_review` сохраняет валидные ответы, но итог `null`, без искусственного
перераспределения веса только на успешно проверенные критерии.

```powershell
$base = 'http://127.0.0.1:8001'
Invoke-RestMethod "$base/api/health"
Invoke-RestMethod "$base/api/dataset/load" -Method Post -ContentType 'application/json' -Body '{"group_id":"DEV"}'
$job = Invoke-RestMethod "$base/api/evaluations/batch" -Method Post -ContentType 'application/json' -Body '{"conversation_ids":["p1-ru-001","p1-en-001"],"output_language":"ru"}'
Invoke-RestMethod "$base/api/jobs/$($job.job_id)"
```

Для контрольного набора укажите полученный от организаторов group_id в запросе
загрузки либо `DATASET_GROUP_ID` в `.env`. Действительный `DATASET_API_URL` обязателен:
при отсутствии возвращается HTTP 503 `DATASET_NOT_CONFIGURED`, данные не имитируются.
Одиночная загрузка поддерживает JSON и `text/plain` со строками `role: text`;
неизвестное время — пустая строка. `MAX_DATASET_BYTES` ограничивает тело загрузки
до разбора JSON; `LLM_MAX_INPUT_CHARS` ограничивает вход модели без обрезки.

## Апелляции и переоценка — этап 4

Апелляция открывается по сохранённому валидному критерию. Карточка содержит
спорный ответ, исходный итог, две соседние реплики вокруг каждого доказательства
и весь `checked_range`. Для одного критерия допускается одна открытая апелляция.
AI-рекомендация проходит проверку значений, ID и цитат, сохраняется в аудите вызовов
и не изменяет ответы. Решение `confirm` сохраняет ответ, `change` обязано изменить;
оба требуют причину. Повторное решение возвращает 409.

`original` и исходные ответы неизменяемы. Решение пересчитывает `final`, хранит
`before_total` и `after_total`. Новые цитаты от имени проверяющего не выдумываются:
ручной ответ помечен `source=reviewer`, исходные доказательства доступны в `original`.
Актуальные токены, включая AI-подсказки, берите из верхнего `usage` карточки.

Сохранение чек-листа создаёт и активирует новую версию; ответ содержит `change_summary`.
Вызов модели необходим для добавленных/активированных критериев и изменений `name`,
`description`, `type`, `allow_na`, `na_condition`, `yes_text`, `no_text`, `scale`.
Изменение только веса, участия в расчёте, секции или порядка требует пересчёта.
Удалённые и отключённые критерии исключаются.

В batch передайте `criterion_ids: ["05"]` для изменённого критерия или `[]` для
автоматического diff/пересчёта. Оставьте поле отсутствующим для полной оценки.
Базой служит последняя валидная completed-оценка по более ранней версии того же
чек-листа и той же редакции транскрипта. Используется её финальный слой с решениями
проверяющего. Если подходящей базы нет — оценивается весь чек-лист. Все семантически
изменённые/добавленные критерии автоматически включаются, даже если их забыли в списке.
Чисто весовые изменения не вызывают модель даже при указании их ID.
Итог всегда рассчитывается по полному новому чек-листу.

В `reevaluation` видны база, реально оценённые и перенесённые ID. Перенесённые
объяснения сохраняют прежний язык, указанный в `baseline_output_language`.
При чистом пересчёте токены и стоимость равны известному нулю — запросов не было.
При неизвестном usage после ошибки сумма неполна: `usage_complete=false`.

Пример изменения одного существующего критерия через API, без изменения остальных.
Замените `CONVERSATION_ID` на загруженный ID. Сохранение сразу активирует новую версию:

```powershell
$base = 'http://127.0.0.1:8001'
$checklist = Invoke-RestMethod "$base/api/checklists/active"
$criterion = $checklist.criteria | Where-Object criterion_id -eq '05'
if ($null -eq $criterion) { throw 'Критерий 05 отсутствует в выбранном чек-листе.' }
$criterion.description = 'Для этой версии требуется конкретная реакция на явно описанное клиентом неудобство.'
$json = $checklist | ConvertTo-Json -Depth 40
$version = Invoke-RestMethod "$base/api/checklists" -Method Post -ContentType 'application/json; charset=utf-8' -Body ([Text.Encoding]::UTF8.GetBytes($json))
$request = @{ conversation_ids = @('CONVERSATION_ID'); checklist_version_id = $version.checklist_version_id; criterion_ids = @('05') } | ConvertTo-Json -Depth 10
$job = Invoke-RestMethod "$base/api/evaluations/batch" -Method Post -ContentType 'application/json; charset=utf-8' -Body ([Text.Encoding]::UTF8.GetBytes($request))
Invoke-RestMethod "$base/api/jobs/$($job.job_id)"
```

Описание в примере — синтетическая конфигурация, не реплика организаторов. Для
замены на другой тип передайте соответствующий `type` и допустимую `scale`, очистите
неподходящие поля предыдущего типа и сохраните новую версию тем же способом.

## Проверки качества и подготовка сдачи

Следующие команды выполняют реальные запросы и расходуют токены. Запускайте CLI-пакеты
последовательно, без одновременно работающего batch другого процесса API. Используйте
новую папку для новой серии; захваты завершённых фаз не перезаписываются.

```powershell
$run = 'data/reports/stage5-run-01'
.\.venv\Scripts\python.exe scripts/quality_check.py dev --group-id DEV --report-dir $run
.\.venv\Scripts\python.exe scripts/quality_check.py repeat --group-id DEV --report-dir $run
.\.venv\Scripts\python.exe scripts/quality_check.py criterion --group-id DEV --report-dir $run
.\.venv\Scripts\python.exe scripts/quality_check.py edges --group-id DEV --report-dir $run
```

Первый запуск фиксирует активную версию чек-листа, SHA-256 файла промпта и группу
в `state.json`. Дальнейшие фазы используют ту же базовую версию и проверяют хэш;
при изменении файла промпта требуется новая серия. Результаты и подробные сырые
ответы сохраняются только в `data/reports/`.

- `dev` обрабатывает все сохранённые диалоги группы, пропуская готовые оценки
  текущей версии и ревизии. До введения prompt_hash на активной версии уже имелось
  восемь готовых оценок без хэша. Они не приписываются новому промпту: отчёт показывает
  отдельную группу `legacy_unknown`. Распределения RU/KZ/EN и звонков описывают
  выбранные результаты; звонки пересекаются с языковыми группами.
- `repeat` выбирает пять диалогов с покрытием языков, звонка и применимой идентификации,
  делает три независимых forced-прогона. Метрики показывают полное совпадение трёх
  ответов, попарное совпадение, покрытие валидными ответами и конкретные расхождения.
  Повторяемость не является сравнением с экспертной разметкой.
- `criterion` заменяет один критерий на отсутствующий в seed критерий `09` про
  необъяснённый жаргон: сначала yes_no, затем тот же ID со шкалой 0–5. Для восьми
  диалогов выполняется частичная переоценка, проверяется перенос остальных ответов
  и независимый пересчёт итогов. Созданные версии сохраняются; исходная активная
  версия восстанавливается после сценария.
- `edges` использует изолированную копию SQLite: три синтетических случая
  (без оператора, одна реплика, отсутствие конкретного вопроса) и самый длинный
  диалог DEV. Показываются число реплик, размер входа, предупреждения, N/A,
  needs_review и ошибки. Модельные ответы не исправляются вручную.

`usage` batch-отчёта учитывает только новые физические вызовы этой задачи.
`averages_new` описывает новые оценки, `averages_selected` — все выбранные, включая
пропущенные. Эти суммы не нужно складывать: пропуск не означает повторную оплату.
Остаточные ошибки `needs_review` доступны в одноимённом списке и в файлах оценок.
Эвристические аномалии распределений — повод для просмотра, а не доказательство
ошибки: группы могут отличаться темами, каналами и сложностью запросов.

## Согласие с ручной разметкой на выборке

Проверены исходные поля всех DEV-записей: готовой эталонной разметки в них нет.
До заполнения вашей разметки метрика согласия отсутствует. Распределения ответов,
успешные HTTP-запросы и зелёные тесты не заменяют экспертную проверку.

```powershell
.\.venv\Scripts\python.exe scripts/export_labeling_sheet.py --group-id DEV --count 10 --output-dir data/reports/labeling
```

Команда выбирает десять диалогов по активной версии и текущей ревизии: разные языки
и каналы, с приоритетом исторических повторов валидации и needs_review. Для явной
версии добавьте `--checklist-version-id VERSION_ID`. Экспорт создаёт CSV UTF-8 BOM
и Markdown с полными транскриптами, критериями, ответами, объяснениями и доказательствами.
Колонки **«мой ответ»** и **«комментарий»** изначально пусты. Заполните только их,
используя точные строковые значения из `allowed_answers`, и сохраните CSV в UTF-8.

```powershell
.\.venv\Scripts\python.exe scripts/labeling_agreement.py 'data/reports/labeling/ИМЯ_СОЗДАННОГО_ФАЙЛА.csv' --output data/reports/labeling/agreement.json
```

Скрипт выводит долю заполненных строк, долю совпадений по каждому критерию и в целом,
а также расхождения. Пустые ответы не считаются ошибками. Если ни одной строки
не размечено, `agreement_percent=null`, а не 0 или 100. Невалидные ответы модели
показаны отдельно и не входят в знаменатель совпадений. Сравнение использует слой
`original`; ручные решения в `final` не подставляются вместо ответов модели.
Перенесённый ответ с источником reviewer также не выдаётся за ответ модели.
Смешанные/неизвестные хэши промпта отмечаются в отчёте. Эта целевая выборка не случайная;
её метрика называется **«согласие с ручной разметкой на выборке»** и не обобщается на весь DEV.

CSV защищён от запуска формул префиксом апострофа; скрипт сравнения восстанавливает
исходный текст. Данные разметки и отчёты разрешено сохранять только внутри
`data/reports/`; в Git они не добавляются. Для повторного JSON-отчёта укажите новое имя.

## Контрольный набор одной командой

Заполните действительный `DATASET_API_URL` локально. Затем команда сама загружает
группу, запускает batch на активной версии, ждёт завершения и печатает итог:

```powershell
.\.venv\Scripts\python.exe scripts/process_control_set.py DEV
.\.venv\Scripts\python.exe scripts/process_control_set.py CONTROL_ID_FROM_ORGANIZERS
```

Повторный запуск безопасен: идентичный импорт не меняет ревизию, готовые оценки
пропускаются. Сводка включает completed/needs_review/failed, время, новые токены,
стоимость по оценкам и среднюю, ошибки валидации и готовые conversation_id.
Код выхода 0 означает завершённый набор без failed/needs_review; 2 — обработка
закончена, но есть такие результаты; 1 — загрузка или выполнение не завершены.

Если URL пуст, живой вызов не имитируется: команда возвращает ошибку. Для проверки
уже загруженного DEV существует только явно выбранный локальный режим:

```powershell
.\.venv\Scripts\python.exe scripts/process_control_set.py DEV --from-db
```

В этом случае `source=local_database`, `network_load_verified=false`;
успех локального сценария не подтверждает доступность API организаторов.

## Репетиция демонстрации

```powershell
.\.venv\Scripts\python.exe scripts/demo_check.py --group-id DEV --from-db --ai-suggest
```

Один запуск проверяет оценку с N/A и доказательствами, апелляцию, отдельное решение,
неизменность original, замену критерия, применение к диалогам и статистику стоимости.
Модель настоящая; ответы и ошибки не подменяются. Для сетевой загрузки уберите
`--from-db` после настройки URL. Локальный режим явно помечает внешнюю загрузку
непроверенной. Можно выбрать `--conversation-id`, `--criterion-id`, `--decision-answer`,
`--decision-reason` и размер переоценки `--batch-size` от 1 до 8.

Сценарий работает в отдельной SQLite под `data/reports/`, основную БД не изменяет.
Решение проверяющего демонстрационное и не считается эталоном. Если выбранный диалог
не получил N/A или оценка невалидна, шаг заканчивается ошибкой, а не вымышленным ОК.
Захваты каждого API-запроса и итоговый `demo_report.json` сохраняются локально.
Повторный запуск требует новую папку `--report-dir`, существующая копия не перезаписывается.

## Ограничения прототипа

- Один процесс API, SQLite и локальная очередь; распределённого планировщика нет.
- Авторизация пользователей и разграничение ролей не реализованы; сервер по умолчанию
  слушает localhost. Доступ к решениям проверяющего в прототипе не разграничен.
- Прерванные jobs не возобновляются автоматически. Повторите batch после проверки
  `items`; уже готовые элементы будут пропущены.
- Списки пока без пагинации; подходят для набора хакатона.
- Денежная единица соответствует введённым ценам провайдера; автоматически не определяется.
- Реальные результаты могут различаться между вызовами. Валидация структуры и цитат
  не измеряет точность относительно Ground Truth.

используется активная версия. Экспорт выбирает последнюю оценку текущей ревизии
каждого диалога по этой версии; последнюю ошибку не скрывает старым успехом.
Экспериментальный чек-лист с критерием 09 не подходит формату сдачи 1.0:
перед контрольным запуском активируйте официальный чек-лист 01–08.

После выдачи контрольного набора заполните `DATASET_API_URL` в `.env` и замените
`CONTROL_GROUP_ID` ниже на точное значение организаторов. Одна команда загружает
набор, проверяет состав и чек-лист до платных вызовов, оценивает, ждёт batch и
выгружает `results/prod/results.json`:

```powershell
.\.venv\Scripts\python.exe scripts/process_control_set.py CONTROL_GROUP_ID --export-results --split prod --team-name TheGoldenDuo
```

`--from-db` разрешён только как явное использование уже сохранённых данных;
он не проверяет сеть. При сетевом запуске экспортируются именно ID, полученные
в текущем ответе API, а не старые записи с тем же group_id. Неполный набор, дубли,
неподходящий канал или демонстрационный чек-лист останавливают процесс до оценки.

Повторная выгрузка идентичных результатов ничего не перезаписывает. Если данные
изменились, после проверки используйте `--replace` у `export_results.py` или
`--replace-results` у `process_control_set.py`; прежний файл сохранится в
игнорируемом `data/reports/submission_backups/`. Запись атомарная; параллельные
запуски экспортёра защищены `.results-export.lock`. Если процесс оборвался,
убедитесь, что он больше не работает, прежде чем вручную удалить оставшийся lock.

Коды завершения: **0** — файл проверен, все записи `ok`; **2** — файл проверен,
но содержит реальные записи `error`; **1** — экспорт не завершён, прежний файл
не заменён. Ошибочный диалог сохраняет ID, `criteria: []`, `score: null` и причину.
Такой файл соответствует формату, но его ошибки следует устранить, если до
стоп-кода осталось время. Файлы с ключами экспортёр сохранять отказывается.

| Внутренний ID | Код сдачи | Тип value | Вес |
| --- | --- | --- | ---: |
| 01 | contact | boolean | 10 |
| 02 | discovery | boolean / null | 15 |
| 03 | identification | boolean / null | 20 |
| 04 | consultation | 0, 5, 10, 15, 20 / null | 20 |
| 05 | empathy | boolean | 15 |
| 06 | dialogue | 0, 4, 7, 10 | 15 |
| 07 | closure | boolean / null | 5 |
| 08 | critical | boolean | 0, отдельный флаг |

`dialogue=7` означает исходную ступень 7 из 10; в итог она даёт 10.5 балла до
перераспределения весов. `evidence_turns` — индексы с 1 по полному исходному
массиву, включая клиента, бота и system. Для пропущенного действия в этот массив
входят реплики проверенного `checked_range`. `rationale` сохраняет объяснение
модели, без ручного исправления ответа. Цитаты evidence, транскрипты, audio_url,
сырые ответы модели и отладочные метаданные в публичный файл не включаются.
Имена моделей берутся из журнала реальных вызовов, включая происхождение
перенесённых ответов, а не из текущего значения META_MODEL. У полностью неудачного
вызова в имени остаётся модель, к которой обращались; все записи остаются `error`.

Скрипты **не выполняют Git-команды**. Перед сдачей нужны проверка файлов, commit и
push в согласованную ветку. Сам локальный файл или локальный commit недостаточен.
После отправки проверьте доступ к обоим файлам без авторизации и передайте
организаторам ссылку на фактическую ветку; не меняйте ветку или видимость
репозитория без отдельного согласования. Час до стоп-кода включает загрузку,
вызовы модели, проверку и push; не откладывайте отправку до последней минуты.

## Проверка файла перед сдачей

Валидатор ничего не исправляет: он читает JSON и источник набора, перечисляет
нарушения и отдельно отмечает проверки, для которых данных недостаточно.
Проверяются UTF-8/JSON, точный состав полей и ID, строгие типы, восемь критериев,
непустые объяснения, номера реплик полного исходного массива, evidence для no/N/A,
название фактически использованной модели и флаг critical. Итог пересчитывается
отдельной функцией на Decimal в `backend/submission_validation.py`, независимо
от `scoring.py`. N/A исключает вес, а critical не обнуляет итог.

```powershell
.\.venv\Scripts\python.exe scripts/validate_submission.py results/dev/results.json --split dev --dataset-source db
.\.venv\Scripts\python.exe scripts/validate_submission.py results/prod/results.json --split prod --dataset-source api --group-id CONTROL_GROUP_ID
```

Для сверки с другой локальной БД есть `--database-path`; конкретную версию
чек-листа можно зафиксировать через `--checklist-version-id`. Код выхода **0** —
PASS, **1** — FAIL, **2** — НЕ ПРОВЕРЕНО хотя бы по одному обязательному источнику.
Проверка по `db` не доказывает доступность API организаторов. При пустом
DATASET_API_URL режим `api` честно возвращает НЕ ПРОВЕРЕНО.

Фиксированный формат сдачи допускает только восемь официальных кодов. Если критерий
05 заменён новым 09, другой тип/шкала или вес больше не соответствует формату,
экспорт остановится с `SUBMISSION_CHECKLIST_MISMATCH` до записи results.json.
Самовольного соответствия 09 → empathy нет; новый критерий не попадёт в criteria
под придуманным кодом и итог файла не будет подменён. При изменении чек-листа
организаторами сначала требуется уточнить разрешённое отображение в формате сдачи.
Обычная оценка новой версии через API при этом поддерживается.

## Омниканальность

`channel` в upload, фильтре списка и ответах API — произвольная строка длиной
1–80 символов, содержащая хотя бы один непробельный символ. Ограничение двумя
каналами снято также с нормализации и SQLite. Один оценщик и один конфиг критериев
используются для `agent chat`, `voice call`, `email`, `whatsapp` и других значений.

Особенности сосредоточены в `backend/channels.py`: `CHANNEL_PROFILES` и профиль
по умолчанию. Чтобы принять новый канал, менять логику оценки не нужно. Если нужны
другие правила времени, добавьте профиль в этот словарь. У voice call ISO 8601 с
таймзоной используется для offset_sec; некорректная метка даёт null и предупреждение.
Другие форматы хранятся как непрозрачная исходная строка. Отсутствующий timestamp
или JSON null нормализуется в пустую строку. Указанная строка не переформатируется.

audio_url может храниться как ссылка, но модель получает только транскрипт:
скачивание/прослушивание аудио, ASR, оценка дикции, интонации и качества звука не
реализованы. `channel_context` добавляется только в промпт, не в REST-карточку.
Порог первой реакции 3 минуты, теги и вложения исключены из оценки явно.

Проверено на реальной muse-spark-1.3 в отдельной SQLite: синтетические email и
whatsapp загружены через API с HTTP 201 и оценены как completed, по 100.00.
Email — 5095 токенов, whatsapp — 5018; один вызов на каждый, исправляющих повторов 0.
Строка времени RFC и отсутствующие/null метки сохранены по правилам выше.
Безоператорный пример вернул 422 `NO_OPERATOR_MESSAGES` до обращения к модели.
Сохранённый захват: [omnichannel.json](data/reports/compliance-20261107/omnichannel.json).
Миграция проверена на копии основной БД: все строки сохранены, включая 65 диалогов,
1268 реплик и 111 оценок; основная БД этой проверкой не менялась:

## Особенности подхода

- Облачная muse-spark-1.3 вызывается через проверенный OpenAI-совместимый Meta API.
  Каждый физический вызов, включая исправления и апелляции, учитывается отдельно.
- Цитата проверяется на принадлежность указанной реплике. При ошибке формата или
  доказательств разрешён один исправляющий повтор; невалидные значения не выдумываются.
- Версии чек-листа неизменяемы; исходный результат и решение по апелляции хранятся
  отдельно. AI-подсказка не принимает решение за проверяющего.
- Частичная переоценка повторно запрашивает только изменившиеся критерии.
  Наблюдаемая экономия 43.91%/47.82% токенов проверена на прежних восьми диалогах;
  один полный baseline был старой версии, поэтому это не контролируемое сравнение.
- Баллы детерминированно считаются на Decimal. Модель возвращает ответы и доказательства,
  а не самостоятельно рассчитанный итог. Хэш промпта фиксирует версию инструкции.
- Опциональный консенсус доступен **только в CLI контрольного набора**: `--runs 3`.
  Три независимых прогона используют одну версию чек-листа, промпт и транскрипт.
  По каждому критерию нужны минимум два одинаковых валидных ответа. Шкалы не усредняются;
  объяснение и доказательства берутся из одного исходного ответа с выбранным значением.
  Если большинства нет, диалог получает error с причиной. Формат JSON 1.0 не меняется.
  REST-карточки показывают отдельные исходные прогоны, а не агрегат консенсуса.

По прежнему полному DEV-прогону средняя новая оценка — 7512.42 токена, суммарное
время LLM с повторами — 28.695 с на диалог. При параллельности 4 batch занимал
416.531 с на 57 новых оценок: 7.308 с на диалог характеризует пропускную способность,
а не задержку отдельного запроса. Цены не заданы; денежная стоимость неизвестна.
Повторяемость 87.50%/90.83% не является согласием с экспертной разметкой. Ручных
ответов пока 0/80, поэтому согласие с ручной разметкой на выборке ещё не измерено.

Для настоящего контроля к команде обработки можно добавить `--runs 3`.
Кеш консенсуса находится в игнорируемом data/reports/consensus-cache и учитывает
версию, хэш промпта, настройки модели и редакции диалогов. Успешные результаты
повторно используются; неуспешный консенсус можно повторить. Расход текущего запуска
находится в usage, всех циклов с повторами — в usage_all_cycles. elapsed_seconds
измеряет весь запуск, llm_duration_seconds — сумму длительностей физических

## Подготовка объединения с фронтендом

Проверка выполнена без merge и без изменений frontend. Снимок фронта в доступном
origin/FRONT: `05a573b`; его docs/backend-openapi.json содержит версию API 0.4.0.
Список 21 маршрута, включая совместимый /api/evaluate, совпадает. По сравнению
с этим снимком изменены только следующие публичные схемы и поведение:

| Изменение | Что учесть фронтенду |
| --- | --- |
| EvaluationResponse.prompt_hash добавлен, string/null | Старые оценки могут иметь null; поле необязательное для клиента |
| channel: enum двух каналов → строка 1–80, не только пробелы | Upload, query-фильтр списка, ConversationResponse и ConversationListItem принимают новые каналы |
| TranscriptInput.timestamp: строка → строка/null, поле можно пропустить | В ответах timestamp остаётся строкой; отсутствующее время возвращается как пустая строка |
| Нет реплик оператора → HTTP 422 NO_OPERATOR_MESSAGES | Показать недостаточность данных; не рисовать нулевую оценку |

channel_context и --runs 3 не являются новыми полями REST API. Консенсус сейчас
относится к CLI и файлу сдачи. CORS использует CORS_ORIGINS через запятую; по умолчанию
`*`, без cookie credentials. Для локального фронта можно разрешить
`http://localhost:5180,http://127.0.0.1:5180`. Определённые API и /docs зарегистрированы
перед условной статикой `/`, поэтому она не перекрывает эти маршруты.

Есть отдельная проблема размещения: FRONT хранит index.html/js/css/assets в корне,
а бэкенд раздаёт только существующую папку frontend/. Обычный merge сам по себе
не сделает корневой index.html страницей FastAPI. Нужен отдельный сервер чистого
каталога статики либо согласованный перенос фронта в frontend/. Не раздавайте
весь объединённый репозиторий с .env как публичную статику. Автоматически файлы
фронта здесь не перемещаются и не создаются.

В инструкции фронта найдено имя META_API_KEY; фактическая настройка бэкенда —
MODEL_API_KEY. API base фронта по умолчанию http://localhost:8001/api, режим нужно
переключить с «Демо» на «API». Реальная связка оценки/апелляции через UI этим аудитом
не проверена. Отдельное ограничение фронта — проверка суммы весов =100, тогда как
бэкенд нормирует итог при другой сумме; это требует согласования с сокомандником.

пустое. FRONT меняет README.md, BACK ведёт README_BACKEND.md; файлы tests/ разные.
Поэтому заранее объявлять конфликт README/.gitignore/requirements нельзя. После
обновления remote refs состав может измениться.

REST API, отдельно фронт и пройдите сценарий оценка → evidence/N/A → апелляция →
решение → новая версия → batch. Commit и push выполняйте только после этой проверки.
