# Интеграция Frontend с Backend

Статус: **частичная.** Каналы данных, диалоги, чек-листы и обработка ошибок проверены на живом Backend; оценка, апелляции и решения
реализованы по контракту, но **не проверены на реальных ответах модели** (нужен ключ Meta AI на стороне Backend). Операторы, Overview и
список оценок Backend не предоставляет.

## Запуск связки

1. Backend (ветка `BACK`, не изменяется этим репозиторием):
   ```bash
   python -m venv .venv && .venv/Scripts/pip install -r requirements.txt
   cp .env.example .env            # META_API_KEY и модель задаются ТОЛЬКО здесь
   .venv/Scripts/python -m uvicorn backend.main:app --port 8001
   ```
   Проверка: `GET http://localhost:8001/api/health` → `{"status":"ok","database":"ok"}`. Не запускайте несколько workers.
2. Frontend (статика, сборки нет):
   ```bash
   python -m http.server 5180
   ```
   Открыть `http://localhost:5180/index.html`, войти (Demo Auth, см. ниже), в шапке Workspace переключить индикатор **«Демо» → «API»**.
3. Другой адрес Backend: в консоли браузера `localStorage.setItem('cqa-api-base','https://host/api')` (или `window.CQA_API_BASE` до загрузки страницы). CORS на Backend: переменная `CORS_ORIGINS`.

## Что работает с реальным Backend

| Функция | Статус |
|---|---|
| Список диалогов, фильтры язык/канал/поиск, деталь, транскрипт с `message_id` | проверено live |
| Импорт диалогов (через `POST /conversations/upload`) | проверено live |
| Чек-листы: просмотр версий, активная, сохранение новой версии, неизменность старых, ошибка 422 | проверено live |
| Ошибки: 404/422, формат `{"error":{…}}`, недоступный Backend (`network`), таймаут, отмена | проверено live + unit |
| Запуск оценки, результат, evidence, N/A, итог | по контракту, **не проверено** (нет ключа модели) |
| Апелляции: создание, рассмотрение (`confirm/change`), итог после решения | по контракту, **не проверено** |
| Операторы, ручная привязка, Overview | **нет на Backend** → в режиме API «не поддерживается» |

## Что нужно, чтобы считать интеграцию завершённой

1. Ключ Meta AI на Backend и прогон сценариев A/B/C на реальных оценках (evidence, N/A, `needs_review`, решение апелляции, итог после решения).
2. Backend: операторы (`operator_id` в диалоге, `GET /operators`, профиль), `GET /evaluations`, серверная пагинация, дата начала диалога, схема `GET /appeals/{id}` и `GET /conversations/{id}/evaluations` с типами в OpenAPI.
3. Реальная аутентификация проверяющего (Demo Auth — не защита).

## Известные ограничения режима API

* Пагинация/сортировка клиентские: на больших наборах (тысячи диалогов) загружается весь список.
* `POST /evaluations` синхронный: кнопка «Запустить оценку» ждёт ответ до 180 с; при ошибке модели (502/429/504) UI показывает ошибку и **не** имитирует результат.
* Заметка к новой версии чек-листа не сохраняется (поля нет в API). В редакторе сохранена проверка «сумма весов = 100», хотя Backend сам нормирует итог.
* Для критериев-шкал при изменении диапазона `min/max` Backend получает сгенерированные описания ступеней; неизменённые шкалы передаются как есть.
* Страница «Оценки» в API — производная от списка диалогов (помечено в `meta`).

## Безопасность

* Ключ Meta AI во Frontend не хранится и не передаётся (поиск по коду: нет `api_key`, `Authorization`, `META_*`).
* **Demo Auth** (`js/main.js`): флаг и e-mail в `sessionStorage`; пароль не сохраняется и не проверяется. Это не защита — любой может выставить флаг в консоли. Не использовать как контроль доступа.
* Текст реплик, комментарии апелляций, причины, цитаты и ошибки экранируются (`esc()`) перед вставкой в `innerHTML`; тест: реплика `<img src=x onerror=alert(1)>` отображается текстом (проверено в UI в режиме API).
* В консоль данные диалогов не пишутся (`console.log` в коде нет).
